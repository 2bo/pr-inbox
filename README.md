# pr-inbox

A Claude Code mod that turns your review requests and your own pull requests into an inbox, ordered by what needs you next: AI summary and risk, an AI review that can approve, a reader for the description and the diff, merging (stacks included), and CI and conflict fixes and replies to review comments with Claude.

![The To review tab: review requests with their risk, how long they have waited, CI and AI review; the bots under their heading; the PRs you approved with why they are still open; and the selected PR's summary and release impact below](docs/screenshot.png)

- **To review**: review requests, the longest-waiting first, then bots' under their own heading, then the PRs you approved that are not merged yet. Each request gets an AI summary, a risk level and its impact on release
- **My PRs**: what needs you (changes requested, CI failed, conflict), then what is ready to merge, what is in review, and what has gone quiet
- **Issues**: the open issues assigned to you, then under their own heading those you created (up to 50 each; one both assigned to you and created by you is listed once, as assigned), the most recently updated first, with their labels, sub-issues closed of all (`SUB`), comment count (`TALK`) and time since the last update (`UPD`). A sub-issue sits under its parent when both are in the same group (`├` `└`), and names its parent otherwise (`↑#12`). An issue updated since you last selected it is marked `●`. The selected issue's description, sub-issues, linked PRs (those that close it, then those that mention it) and latest three comments show under the list; `d` reads it whole (every comment, the latest 100), `p` puts its link in the prompt to ask Claude about it or have it worked on and `c` closes or reopens it. Nothing the tab fetches is sent to a model unless you ask with `p` (an issue a PR's description links to is read by the AI review, `v`, on its own; see [Security](#security))
- A status line under the prompt keeps the counts in view, and new review requests come as a toast and an OS notification (a newly assigned issue as a toast, and an OS notification with `desktop_notify` on `all`)

Tested with Claude Code v2.1.289. Mods need v2.1.287 or later.

## Requirements

- [GitHub CLI](https://cli.github.com/), signed in with `gh auth login`. The mod reads, approves and merges through `gh`, as the account it is signed in to
- Optional: [ripgrep](https://github.com/BurntSushi/ripgrep) (`brew install ripgrep`, or your package manager), to find the Claude Code session that made your PR (`session “…”` in the details under the list, and `t`). Without it, pr-inbox tries the ripgrep inside Claude Code; if that does not work either, the details say `session unknown` and `t` says why
- Optional: [gh stack](https://github.com/github/gh-stack) (`gh extension install github/gh-stack`) to merge stacked PRs, and [ghq](https://github.com/x-motemen/ghq) so `c` and `g` can find (or fetch) your clone of a repository

## Install

In Claude Code:

```
/plugin marketplace add 2bo/pr-inbox
/plugin install pr-inbox@pr-inbox
```

Or from the shell: `claude plugin marketplace add 2bo/pr-inbox && claude plugin install pr-inbox@pr-inbox`.

## First run

1. **Before anything else**: by default each review request is analyzed as soon as Claude Code starts, which sends its title, description and diff to the model you use (see [What is sent](#security)). For work code, set `analysis` to `when opened` or `off`, or narrow it with `org_filter`, first (`/config`)
2. The status line appears under the prompt: `to review 3 ⚙2 · ▲1 high │ my PRs ✗1 fix · ✓1 ready · …2 in review │ issues 4` (issues assigned to you, only when there are some; the Issues tab adds those you created: `issues 4 · 12 yours`)
3. `/pr-inbox` opens the pane. Keys reach it while it has the focus: `ctrl+x tab` moves between the prompt and the pane, `Esc` goes back to the prompt
4. The bottom line lists the keys for the selected PR, each labeled with what it does, the most used first (`d` read, `a` approve, `v` AI review, `e` explain). `u` shows every key and what each mark means, and a key that does nothing for the selected PR says why

## Reading the list

One line per PR. From left to right:

| Column | Marks |
| :- | :- |
| Marks | `▸` selected · `●` updated since you last selected it · `⚙` a bot · `┌ ├ └` a stack, bottom (the next to merge into the base branch) to top: one made with gh stack, or PRs opened on each other's branches |
| RISK (To review) | `▲ HIGH` · `◆ MED` · `○ LOW` from the analysis · `…` analyzing · `·` not analyzed · `✎ DRFT` a draft (its risk is in the details under the list) |
| STATE (My PRs) | `✗ CONF` conflicts with its base (`c`) · `✗ FIX` needs you (changes requested, CI failed) · `✓ RDY` ready to merge · `… REVW` in review · `⇢ AUTO` auto-merge on: GitHub merges it when ready · `○ ASK` waits on a review, but nobody is asked (`w`) · `✎ DRFT` a draft · `◇ OLD` no update for `stale_days` · `⏸ SNZ` snoozed · `⟳ WIP` Claude is fixing its CI or conflict (`c`) or addressing its review threads (`g`) · `⇡ PUSH` a fix waits for your push · `⇡ POST` replies wait for your `y` (`fix_push` or `fix_reply` `ask`, a turn cut short, or a push refused) · `⚑ YOU` drafts held for you (`g`; the PR is listed under what needs you) |
| Approved by you | `↻ RE` changed since you approved (re-review) · `✎ DRFT` a draft · `… REVW` waits on other reviews · `◌ CI` running · `✗ CI` / `✗ CONF` / `✗ CHG` what blocks it · `✓ RDY` ready to merge |
| PR, TITLE | Links to GitHub (Cmd+click in a terminal that supports hyperlinks) |
| AGE | `▰▱▱` how long it has waited: one cell at 4 hours, two at a day, three at three days |
| CI | `✓` passed · `✗` failed · `◌` running · `·` none. Judged from the latest run of each check, so a job that failed and then passed on a re-run counts as passed |
| AI | `✓` passed or approved · `✗` blocked · `?` passed, waits for you · `·` no AI review |
| Issues | `●` updated since you last selected it (a newly assigned issue too; one you just filed only once something happens on it) · `✓` closed here (`c` reopens) · `├` `└` a sub-issue under its parent in the same group · `↑#12` its parent, in the other group or not listed · SUB sub-issues closed / all (green when all are closed) · TALK comments · UPD time since the last update |

Under the list, the selected PR's details: the summary, why that risk, the release impact, one line of facts (the branches it merges into and from, `develop ← feature/login`, and its place in a stack), the AI review and, for your PRs, the failed checks. Last come the description and the latest three comments and reviews, drawn as markdown as GitHub would (`y` shows them as written); they are fetched once the selection rests on the PR. Each fact is said once, and hints name the key that acts on them (`a: approve`, `m: merge now`). When the details do not fit, `n` pages through them, and the mouse wheel and PgUp / PgDn scroll them both ways; the description never takes the list's half of the pane. Nothing is folded: bots, the PRs you approved and old PRs each have a heading; only snoozed PRs wait behind `z`.

A stack is listed together, bottom first, so the PR that merges next comes first. Besides stacks made with [gh stack](https://github.com/github/gh-stack), a PR whose base branch is the head branch of another open PR in the repository counts as stacked on it (`stack · 2/3 on #101`), among the PRs pr-inbox lists (yours, your review requests and the ones you approved). Branches of forks are left out, and so are long-lived branches (the repository's default branch, `main`, `master`, `develop`, `development`, `dev`, `staging`, `production`, `trunk`): PRs into `develop` do not sit on a `develop → main` release PR.

Under the list, the details of one of your PRs are split by kind, one line each: where it stands (what needs you, in yellow; ready to merge; or what it waits on, and whether auto-merge is on), its keys, the facts, and the Claude Code session. When Claude is working on it, or something waits on you there, that comes first on a line of its own, and the line after it stays uncolored. A review request keeps its facts on one line.

## Asking for reviews

`w` on your PR opens the reviewers in the pane. **On this PR** lists who is asked now and who reviewed, with their verdict and, for someone a team assigned, the team (`via @acme/web`). **Suggested** ranks people and teams by GitHub's suggestions, who reviewed your recent PRs in that repository, who reviews there often, and who you asked last time; you and the people already on the PR are left out. `f` finds anyone who can be asked by login or name, and the repository's teams.

`x` (or `1`-`9`) checks and unchecks, and the line above the keys says what `y` will send: `+` ask, `↻` ask again, `−` take a request back. Nothing goes to GitHub before `y` (or `s`, see below); `q` leaves without sending. (Before 1.8.0 `s` sent. It still does for now, with a toast saying `y` is the key, and stops in a later major version.)

- **Repositories reviewed by a team.** When you asked a team on half or more of your recent PRs there, the team comes first, and is checked when nobody is on the PR yet: `w` then `y` asks it. A team with GitHub's code review assignment says so (`assigns 1 (round robin)`); after you ask it, pr-inbox waits a few seconds and tells you whom it picked. People a team picked at random do not count as the ones who usually review your PRs
- **After a push.** Someone who requested changes, or approved a commit before your push while GitHub still wants an approval, is checked to be asked again (`w: re-request @mika` on the row). It goes to them, not to their team, which would pick someone else
- **Nobody asked.** A PR that waits on a review with no one asked shows `○ ASK` instead of `… REVW`

## Fixing CI or a conflict

`c` on your PR with a failed CI or a conflict with its base (or `/pr-inbox fix <repo#number>` from the prompt: the conflict if there is one, else the CI) lets Claude fix it:

1. The panel names the failed checks or the conflict and what will happen. Nothing starts until you press `1` (fix CI with Claude) or `3` (resolve the conflict with Claude) and `y`
2. pr-inbox finds your clone (the session's directory, or the one `ghq` knows, or `ghq get` after `y` in the clone panel) and makes a git worktree of its own at the PR's head: `~/.cache/pr-inbox/worktrees/<owner>/<repo>/pr-<n>`. Your checkout is not touched
3. Claude reads the failed logs and fixes them, or merges the base (fetched just now) into the PR and resolves the conflict, never by a rebase; it runs the tests and commits. The row shows `⟳ WIP`. It cannot push, merge, approve or comment: pr-inbox refuses those
4. When the turn ends on its own, with `fix_push` on `auto` (default), pr-inbox pushes its commits to the PR's branch, exactly the commits not on the branch as fetched, up to the worktree's HEAD, never forced; a toast and the transcript say what went. With `ask`, or when the turn was cut short or the push was refused, nothing opens by itself: the row shows `⇡ PUSH`, a toast names the PR, and the hint under the prompt says `⇡ fix ready` until it is pushed or forgotten. `c` opens the push panel: exactly the commits a push would send (after a merge, the base's commits it brings in are counted, not listed: they are on GitHub already), pinned to the worktree's HEAD; `y` pushes, `d` shows the diff first, `x` forgets the fix (its commits stay in the worktree; `c`, `1` (`3` for a conflict), `y`, then `3` in the worktree panel push them later). A worktree with commits left from an earlier fix asks first: `1` go on from them or `2` start again

## Addressing review comments

`g` on your PR with review threads that wait on you (or `/pr-inbox address <repo#number>` from the prompt) lets Claude go through them. A thread waits on you while it is unresolved and its last comment is someone else's, so one you answered drops out until the reviewer writes again. One fix runs at a time, in the same worktree as `c`'s: while a fix runs or waits on the PR, `c` and `g` both open it, whichever started it.

1. The panel names each thread (file and line, and who had the last word) and what will happen. Nothing starts until you press `y`
2. Claude gets the threads' ids only and reads them itself with read-only `gh` commands. For each it decides: `fixed` (it changes the code and commits), `declined` (no change, and why), `question` (it asks the reviewer) or `needs_you`: a thread it should not settle alone (a spec or design choice, a likely disagreement with the reviewer, a large change of scope, an unclear intent), for which it changes no code and writes why it hesitates and a draft reply or the options. It writes its replies to `~/.cache/pr-inbox/replies/<owner>/<repo>/pr-<n>.json`, outside the worktree; replies left from an earlier turn are removed first. It cannot reply, comment, resolve or push: pr-inbox refuses those
3. The commits are pushed as a CI fix's are (`fix_push`). A turn that made no commit pushes nothing, and only its `declined` and `question` replies can go
4. With `fix_reply` on `auto` (default), once the turn ended on its own and its push went, pr-inbox posts each reply to its thread (`fixed` ones say the commit they went out in) and one toast says what the turn's end did (`✦ acme/app#21: pushed 2 commits, posted 3 replies · ⚑ 1 thread needs you · g: read it`); the transcript has each step. When the push did not happen (`fix_push` `ask`, a turn cut short, a push refused), the replies wait with it and go right after `y` in the push panel. With `ask`, nothing is posted by itself: the row shows `⇡ POST`, a toast names the PR, and `g` opens the replies panel: a row per reply (what it is, its thread, the reviewer and its text; `j` / `k` show each in full); `y` posts them all, `x` forgets them. Threads are never resolved: that stays with the reviewers
5. A `needs_you` thread is held, whatever `fix_reply` says: nothing about it is posted by itself. With `fix_reply` on `auto`, so is a `declined` reply to a person (the last comment not a bot's): saying no to a reviewer is left to you, whatever Claude judged; a decline to a bot goes on its own. The row shows `⚑ YOU` and `⚑ 1 thread needs you · g`, the PR is listed under what needs you, a toast and the hint under the prompt say so, and nothing opens. `g` opens the held panel: each held thread a row (file and line, reviewer, why it is held, and the draft, the selected row in full; `j` / `k` move). None is checked to start with: `x` or its number checks a draft, `y` posts exactly those, and the others stay held for later; `q` leaves them all; `r` forgets them all (nothing is sent) and opens `g`'s panel to start over, where `y` starts the new turn. To talk one over first, `p` on the PR asks Claude about it. A held thread drops out once it no longer waits on you (you answered it on GitHub, or it was resolved)

## AI review and approve

`v` on a review request runs a review from several perspectives, each an independent model call, and approves the PR when it passes:

1. **Gates, checked in code**: not a draft, no merge conflict, no reviewer requested changes. A failing or running CI does not stop the review: it is a ⚠ warning, and such a PR is never approved without you
2. **Screening**: the description, diff, comments and the issues and PRs it links to (whose comments anyone can write) are checked for instructions aimed at an AI (prompt injection) by a small model, and the PR is checked for changes to AI instructions (CLAUDE.md, `.claude/` rules, skills, subagents and the like). What happens next depends on who decides: when the approval would go through without you (`ai_approve` `auto` for an author it applies to), any of these stops the review; when you approve in the approve panel, the review goes on and they are shown as ⚠ warnings in the pane, the approve panel and the transcript
3. **Reviewers**, in parallel on `review_model` (Sonnet by default). Each first says what else it needs to read (files at the PR head, code searches, upstream release notes); the mod checks the request, fetches and screens it, then the reviewer reviews:
   - Purpose & scope: does it do what the description and the issues it closes ask, without needless complexity or unrelated changes. It reads up to 5 issues and PRs in repositories of the PR's owner: first those the description links to, from the top (links inside HTML comments and code don't count), then those the PR closes from the sidebar. The rest are not read, and the reviewers are told so. Issues it closes are the purpose; those it only mentions are context
   - Correctness & compatibility: bugs, breaking changes, migrations, rollback, performance
   - Tests: is the changed behavior tested
   - Security & secrets
   - Conventions: the repository's CLAUDE.md, AGENTS.md, REVIEW.md, CONTRIBUTING.md and patterns. These guides, the rules in `.claude/rules/`, and any AI instruction a reviewer asks for (skills, subagent definitions, commands, nested CLAUDE.md, Cursor or Copilot instructions) are read from the base branch, so a PR cannot rewrite the rules it is reviewed by. They talk to AI by design, so they are given apart from the PR content and not screened for injection
   - For **Dependabot and Renovate** PRs, instead: **Upgrade impact** (every package that changes, directly or in the lockfile; upstream release notes and changelogs; whether this repository uses what changed) and **Supply chain**
4. **Verification**: important findings (confidence 80+) go to a verifier that tries to refute them against the code
5. **Decision, in code**: it passes only when every gate holds, nothing looked like an injection, every reviewer answered, no important finding survived and the PR got no new commits. Nits do not block

Under the PR, the outcome comes first, then the gist in one sentence in your `language` (`→ Blocked: …`, written by the analysis model from the reviewers' answers), then each perspective's conclusion in a sentence or two: ✓ no problems, ✗ blocks the approval, △ found something that does not block (low confidence, or refuted by the verifier), ? could not tell. `i` shows every finding with its evidence and a link to the line. The conclusions and findings are also written to the transcript.

Only problems within each reviewer's perspective count, and the same problem found from two perspectives is shown once. The result is kept for the reviewed commit, so it is still there after a restart; when new commits arrive, the row says the review is of an older commit.

When it passes, `ai_approve` decides: with `confirm` (default) nothing breaks in on what you are doing: the row and a toast say it passed, and `a` approves it, its panel listing the review's notes and warnings. `auto` approves at once for PRs from members and collaborators of the repository and from Dependabot or Renovate (the review on GitHub then says the pr-inbox AI review approved it on its own, and so do the toast and the pane), and leaves anyone else and forks to `a`. `b` reviews every bot PR without moving your selection, then opens one approve panel for those that passed (and any that passed before), naming each commit; with every bot PR reviewed, it only opens the panel. Every approval is pinned to the reviewed commit. A review stopped by a gate (draft, CI failing, conflict, changes requested) says it did not run.

With `auto_review` set to `bots` or `review requests`, the review runs without `v` when a review request (or, with `bots`, a bot PR) arrives or gets new commits, one at a time and longest-waiting first, in interactive sessions only (not in `claude -p` runs). It is shared by your sessions: a PR one session reviews is left alone by the others, and at most 6 reviews start an hour across all of them (the plugin store has no lock, so two sessions that take a PR in the same moment may rarely both review it, or start a 7th). Snoozed PRs, those a gate would stop and those whose CI is still running wait. A commit already reviewed, or whose review you cancelled, is not reviewed again; a review that failed (a reviewer gave no answer) is tried again later, up to 4 times. Cancelling an automatic review with `v` pauses `auto_review` for an hour (`v` still reviews). With `analysis` on `when opened`, it waits for the pane too. What happens when it passes is the same as after `v`: `ai_approve` decides. Its reviews say `AI review (auto)` in the pane, each round ends with one toast (`auto_review: 2 passed (a: approve), 1 blocked`) instead of one per PR, and a review request it has not reviewed yet says why under its row (CI still running, a gate, the hourly limit, a pause, a retry later). The status line says `auto paused` or `auto at limit` while it waits.

A review makes about two Sonnet calls per perspective plus the verifier and several small screening calls, on your plan. It usually takes under a minute.

Change them with `/config` or `/plugin configure`.

| :- | :- | :- |
| `org_filter` | (empty) | Only show PRs and issues in this GitHub organization |
| `stale_days` | 30 | List your PRs not updated for this many days under Old |
| `refresh_minutes` | 5 | How often to fetch from GitHub |
| `summary_model` | sonnet | The model that writes the summary, risk and release impact |
| `desktop_notify` | review requests | OS notifications for `review requests`, `all` (also approvals, changes requested and CI failures on your PRs, and issues newly assigned to you) or `off`. Uses `osascript` on macOS and `notify-send` on Linux. On macOS, allow notifications for Script Editor in System Settings if none appear |
| `analysis` | auto | When review requests are analyzed: `auto` (from startup), `when opened` (once you open `/pr-inbox` in the session) or `off` |

| `approve_comment` | (empty) | The comment of an approval you make with `a` or `b`, such as `LGTM`, shown in the approve panel before `y` and posted on each approval on one line, with control and invisible characters removed, exactly as the panel shows it (an @mention in it notifies). Empty sends none. Approvals by `ai_approve` `auto` keep their own comment |

| `fix_reply` | auto | Claude's replies to the review threads of your PR (`g`): `auto` posts them when the fix turn ends on its own and its push went, `ask` waits for `y` in the replies panel. | `auto_review` | off | Run the AI review on its own when a review request arrives or gets new commits: `bots` (bot PRs only), `review requests` (all) or `off` |
| `theme` | dark | `dark` (neon) or `light` (deeper colors for a light terminal) |
| `glyphs` | unicode | `ascii` draws every mark as one plain character, for terminals that draw symbols such as ━ ● ◆ ⚙ two cells wide |
| `review_model` | sonnet | The model of the AI review |
| `review_purpose` / `review_correctness` / `review_tests` / `review_security` / `review_conventions` | (built-in) | Instructions for each reviewer. `off` skips that perspective |
| `review_dependency_impact` / `review_supply_chain` | (built-in) | The same, for Dependabot and Renovate PRs |
| `explain_prompt` | (built-in) | What `e` asks about a review request. `{url}` becomes the PR URL |
| `risk_high` / `risk_medium` / `risk_low` | (built-in) | What counts as each risk level in the analysis |
| `release_impact` | (built-in) | How to judge the impact on release (yes / no / unknown) |
| `language` | auto | The language of the AI summary, risk and release impact |

Leave the prompt settings empty to use the built-in text. Whatever you write, the mod still adds the instruction to read comments and linked issues (for `e`), and the rules that keep PR content untrusted and `e` read-only. Changing the criteria redoes the stored analyses.

The menus are in English. The AI analysis and its labels follow `language`:

1. `language` set to anything other than `auto`, such as `English` or `Japanese`
2. Otherwise Claude Code's [`language`](https://code.claude.com/docs/en/settings-reference#language) setting
3. Otherwise the terminal locale (`LC_ALL`, `LC_MESSAGES`, then `LANG`)
4. Otherwise English

The labels are in Japanese when the language is Japanese, and in English otherwise. The analysis itself is written in whatever language is chosen.

The analysis calls the model once per PR, on your plan. Results are stored with the PR's update time and language, and are redone only when the PR changes or the language does. A failed analysis is retried after 15 minutes, then 30, 60 and 120, and then left until the PR changes. At most 30 analyses start in an hour.

When a PR is too large to read whole (more than 30,000 characters of diff, 4,000 of description or 300 files), the analysis says so (`judged on part of the PR`) and never rates it low risk.

## Security

- **PR content is untrusted input.** Anyone who can open a PR and request your review controls its title, body, diff and CI output, and may plant instructions aimed at the model
  - The analysis call has no tools and only returns text. The PR content is fenced with a random marker, and the model is told not to follow instructions in it. Invisible Unicode tag characters are removed first
  - When you press `e`, that turn runs under a read-only guard enforced by the mod: only Read, Grep, Glob and the read-only `gh pr view`, `gh pr diff`, `gh pr checks`, `gh issue view`, `gh run view`, `gh run list`, and `gh api` GET requests for a PR's or issue's comments and reviews can run. Edits, other commands, web access, subagents, approvals, comments and pushes are refused, even if your permission mode or allow rules would let them through. If the guard itself fails (an error or a timeout), the call is refused, not let through. The guard ends with that turn; anything you ask next runs with your session's usual permissions
- **AI review (`v`).** Built along Anthropic's guidance on indirect prompt injection and the dual-LLM pattern. The approval is decided in code from the reviewers' structured answers, never by a model. The review's models have no tools: they cannot run commands, read local files, reach the network or write anything. They read only what the mod fetched: the PR under review; up to 5 issues and PRs the description links to or the PR closes, only in repositories of the PR's owner (links to other owners' repositories are not read); and, for dependency updates, upstream release notes and files on GitHub. What they ask to read is validated first. The PR's author picks the linked issues: a private issue of that owner named in someone else's PR is read with your `gh` and sent to the model too, and can show up in findings: read them before you post them with `s` to a PR others can see. Content reaches them as JSON labeled as untrusted, screened for injected instructions, with invisible characters stripped. Any error, timeout or unparsable answer blocks the approval; a suspected injection blocks it when no person approves, and is a ⚠ warning when you do. `auto` is still a choice to trust an AI judgment: keep it to repositories where that is acceptable, and keep branch protection and required reviews as the last line
- **The analysis is a hint.** Do not approve on the strength of the risk or impact judgment. Approve runs only after you press `y` in the approve panel, which names the commit on screen in full (`acme/app#11 at abc1234`) and the `approve_comment` that goes with it; any other key leaves it or does nothing. No model can press keys in the pane. The approval is pinned to that commit, and it is refused if the PR got new commits in the meantime. Turning on "Dismiss stale pull request approvals" in your repositories' branch rules adds a second line of defense
- **Merging.** `m` merges only after you pick a method with its number key in the merge panel (none is picked for you) and press `y`; the panel's line above the keys says exactly what `y` sends. It is offered on your own PRs and on bot PRs (dependabot, renovate …) on To review, never on another person's PR. A single PR's merge is pinned to the commit on screen, and the panel names the branch it goes into (for a PR opened on another PR's branch, that branch). A gh stack merge goes through `gh stack merge`, which cannot be pinned to commits: the panel says so and lists every PR that goes, and GitHub still applies your branch rules to each
- **Auto-merge.** On a PR that is not ready, the same panel turns GitHub's auto-merge on (`gh pr merge --auto`), pinned to the commit on screen. The merge itself is GitHub's, later, at whatever commit the PR is at then: auto-merge stays on through pushes by people with write access, and your branch rules decide when it merges. If GitHub already finds the PR ready, it merges at once. Turning it off is `y` in its panel too. Never on a PR in a gh stack (it would land in the branch below instead of going with its stack), and not offered where the repository's settings allow no auto-merge (`autoMergeAllowed`)
- **Displayed text is sanitized.** Terminal escape sequences, control characters, bidirectional override characters and invisible characters are stripped from PR and issue titles, author names, labels, check names and model output before they are drawn. Issues assigned to you and issues you created (Issues) are fetched in the same `gh` request as the PRs (`is:issue is:open assignee:@me` and `is:issue is:open author:@me`, narrowed by `org_filter`, the 50 most recently updated of each, and the pane says when there are more); the selected one's description, latest 100 comments, sub-issues and linked PRs with `gh api graphql`. They are drawn the same way as a PR's description and comments, and what the tab fetches goes to no model. Only when you press `p` on an issue and send a prompt with its link does Claude read it, with whatever tools your session's usual permissions allow (not read-only; see `p` below), told to treat the issue as someone else's input. The same issue can still reach one by another way: when a PR's description links to it or the PR closes it, the AI review (`v`) reads it for that PR, as described under AI review. The diff (`d`) is drawn by Claude Code's own highlighter, line by line with the same characters stripped (tabs kept), and is never sent to a model. The description and the comments (in the details and in `d`) are drawn by Claude Code's markdown renderer with the same characters stripped and HTML comments removed; they are fetched with `gh pr view` and never sent to a model. Links in them are the author's, drawn as written, except that local `file:` links do not open. pr-inbox's own links open only canonical https URLs. Failed-check links point wherever the CI system says, which may be a third-party site
- **What is sent, and when.** With `analysis` on `auto`, as soon as Claude Code starts (including `claude -p` runs and sessions in other projects) and on every refresh, each review request that has not been analyzed yet is sent to the model Claude Code is configured with (Anthropic, or your Bedrock, Vertex or gateway setup), under your account: its repository and number, author, title, list of changed files, description (first 4,000 characters) and diff (first 30,000 characters). You do not have to open the pane. Follow your organization's rules for work code: narrow it with `org_filter`, or set `analysis` to `when opened` or `off`. `auto_review` (off by default) sends what the AI review reads of a PR (the same content, and the files and searches its reviewers ask for) the same way, without you pressing `v`, at most 6 reviews an hour, in interactive sessions only; `analysis` on `when opened` holds it back until you open the pane, `off` does not
- **Pictures in the reader.** Opening the reader (`d`) on a PR whose description attaches pictures on GitHub asks GitHub for the description as HTML (`bodyHTML`), then downloads those pictures with `curl`, only from `private-user-images.githubusercontent.com`, only over https, with no redirects and without your curl config. No token is sent: the address GitHub signs for you is the credential, and pr-inbox never draws, logs or stores it. Each file is removed from `~/.cache/pr-inbox/images` as soon as it is read (if that fails, a toast names the folder to delete), and what stays in memory goes with the reader. A picture from any other address is not fetched, so no tracking pixel in a PR sees you. Pictures go to your terminal and never to a model. Your terminal decodes them, and the PR's author picks them
- **Posting from the pane.** pr-inbox writes to GitHub only after you answer: approve (`a`, `b`), merge or auto-merge on and off (`m`) and the AI review's findings as a review (`s`), push a CI or conflict fix (unless `fix_push` is `auto`, below), or re-run failed jobs (`c`), push a fix of review comments and post its replies (`g`, unless `fix_push` or `fix_reply` is `auto`, below), and close or reopen an issue (`c` on Issues: `gh issue close <number> -R <owner/repo> --reason` with the reason you picked, or `gh issue reopen`, only for an issue at its own github.com address, and nothing is sent when GitHub has it so already), each after `y` in their panel in the pane, which names what is sent and opens only when you press its key (never by itself, so a `y` meant for something else cannot land in it). Findings are posted under your name with @mentions defused, as the text was written by a model from someone else's PR. Replies to review threads (`g`) are posted only by pr-inbox, below. Review requests (`w`) go out when you press `y` in the reviewers picker (or `s`, which still sends until a later major version), exactly as the line above the keys lists them, and only for logins and teams in GitHub's own format. No model chooses or sends them
- **`p`.** Your prompt with the PR's or issue's link in it, as you see it. `p` only saves you pasting the link, so its turn runs with your session's usual permissions, as if you had pasted it yourself, not under the guard of `e`: Claude Code's permission mode judges what Claude may do. Manual mode asks before each action that is not read-only; Auto mode's classifier blocks some actions that look driven by content Claude read, but does not guarantee it. Accept-edits mode, don't-ask mode, your allow rules and `--dangerously-skip-permissions` let actions through without asking, so instructions planted in a PR or an issue can be acted on. A note beside the prompt tells Claude to treat the PR's or issue's text as data and to tell you about instructions in it, but nothing in pr-inbox enforces that. For a PR written by someone you do not trust, `e` is the read-only way to have it explained (it does not take your own question); issues have no read-only ask, so read untrusted ones without bypassing permissions
- **What is stored locally.** In Claude Code's plugin store (`~/.claude/plugins/store/`): the URLs of your review requests and assigned issues and the state of your own PRs (to notice changes), each analysis (summary, risk, release impact), each AI review's findings, which PRs `auto_review` is reviewing or will retry and when it started its recent reviews, snoozed PRs, which updates of PRs and issues (assigned to you or created by you) you have seen, and the reviewers you last asked in each repository (to suggest them again). Analyses of PRs that are no longer open are deleted on the next refresh
- **Fixing CI or a conflict (`c`).** The fix is an ordinary Claude turn with your session's permissions (your permission mode and allow rules apply), working in a separate worktree, never in your checkout. While it runs, pr-inbox refuses its `git push`, and `gh` merges, reviews, comments on PRs and issues, review requests and other writes (`gh api` POST/PUT/PATCH/DELETE, `gh api` with fields (`-f`, `-F`, `--field`, `--raw-field`, `--input`, a value joined on as in `-fbody=…` or short flags run together as in `-ifbody=…` too), which makes it a POST, and to be safe a `GET` with fields too, as telling which `GET` is its own takes a shell (a read puts its parameters in the URL), and GraphQL mutations or GraphQL read from a file): those stay with you. The check reads the command's text as one line, with quotes and backslashes taken out; it is not a sandbox, and a command built while it runs (a variable, `$(…)`, a script) can get past it, so your permission mode is still what keeps the rest in check. If the guard itself fails (an error or a timeout), the tool call is refused, not let through, whatever the tool, and the fix then waits for you as a turn cut short does: nothing is pushed or posted on its own. The push panel lists exactly the commits a push would send (those not on the branch as fetched; after a merge, those already on the base as fetched are counted instead of listed), says when the turn was cut short, and a worktree with commits left from an earlier fix asks before going on. It opens only when you press `c`, never when the turn ends. It is pinned to the worktree's HEAD when it opened: if Claude committed since, nothing is pushed. CI logs, code and the PR text are written by tools and other people, so the request tells Claude to treat them as data. A conflict is resolved by merging the base in, so the push stays a fast-forward. With `fix_push` on `auto` (default), a fix turn that ends on its own is pushed without asking, by pr-inbox and not by Claude (its own `git push` stays refused), only to that PR's branch, only while GitHub still has the PR open on that branch (a PR merged meanwhile gets nothing, so a deleted branch is not brought back), and pinned to the worktree's HEAD read when the turn ended (a fix you stopped following with `c`, `2` is not pushed): the commits are Claude's work under your name, so set it to `ask` to read them first. Otherwise pr-inbox pushes only after `y` in the push panel, exactly that commit (`git push origin <sha>:refs/heads/<branch>`) to the PR's own branch, never with force; your PRs from forks are left out
- **Addressing review comments (`g`).** The same fix turn as `c` (your session's permissions, its own worktree, the same refusals: no push, no `gh` comments, reviews or other writes, no GraphQL mutations, so Claude cannot reply or resolve a thread itself), pushed the same way (`fix_push`). The threads are fetched right after the PRs, in one more `gh api graphql` request for your own PRs that have any (their ids, file, line and who wrote the last comment, never their text; if it fails, `g` is just not offered) and the request names them by id; the comments, written by other people, are read by Claude in the turn, and the request tells it to treat them as data. Its replies come back as a file outside the worktree, and pr-inbox keeps only replies to the threads it named, each thread once, with one of the four actions, at most 30, each cut to 2,000 characters, with control, bidirectional, invisible and tag characters and HTML comments removed and @mentions defused, and a line saying Claude wrote it and pr-inbox posted it. They are posted under your name, one `addPullRequestReviewThreadReply` per thread (`gh api graphql`, the body on standard input), never resolving a thread, only after the PR is read again: still open, still yours, and at the commit just pushed. A `fixed` reply goes only once its commit is pushed. With `fix_reply` on `auto` (default) they go without asking when the turn ends on its own (not for a fix you stopped following, and not when the push did not happen: then after `y` in the push panel); the text is Claude's, written after reading other people's comments, so set it to `ask` to read every reply first in the replies panel, where only `y` posts them. A `needs_you` draft is never posted without you in either mode, nor with `auto` a `declined` reply to a person (the thread's last comment not by a bot: a GitHub App, or a login ending in `[bot]`), a rule in code whatever Claude judged: it waits in the held panel, unchecked, until you check it and press `y` (then the same checks, without the commit one, as it goes with no push); Claude's `why` is only drawn (cleaned, at most 300 characters), never posted
- **Sessions (`t`).** To show which session made your PR, pr-inbox reads with `rg` (ripgrep: the one on your `PATH`, or else the one inside Claude Code, started through a link pr-inbox makes at `~/.cache/pr-inbox/bin/rg`) and `grep` the rows Claude Code writes in its transcripts under `~/.claude/projects/` for that: the PR links (what `claude --from-pr` uses; Claude Code also writes one when a session pushes to a PR made elsewhere, so a session counts as having made the PR only when its first link comes within 2 minutes of the PR's creation, and otherwise the last session to link it is shown as having worked on it), the session titles and the folder each session started in (and, when you send with `t`, the permission mode it last ran in), and the session list under `~/.claude/sessions/` with `ps` to see which are open. They are only drawn (sanitized; the id in full), on your own PRs, and never sent to a model or stored, with one exception of yours: `4` puts the session's id in the prompt box, where you see it, and it reaches a model only if you send that prompt. `t` sends only what you typed, as an argument to `claude --bg --resume <id> --`, never through a shell, and only after Enter, with `--permission-mode` set to the mode the session last ran in, which the field shows before you send. It never takes `permissions.defaultMode`, which may allow more. Bypass permissions and Don't ask, which act without asking, are lowered to Manual, as is a session whose transcript notes no mode: a session in Manual asks before acting, and `claude attach` opens it to answer. Your allow rules still apply
- **Access.** All GitHub access goes through `gh`; the mod holds no token. OS notifications go through `osascript` or `notify-send`, with the text passed as arguments, never as script. Commands run as argument lists, without a shell

## Development

```bash
pnpm install
claude --plugin-dir .   # run the working copy; loading once also writes the type declarations to .claude-plugin/types/ (needed by typecheck)
pnpm run check          # validate (--strict) → tsc → Biome → claude plugin test
```

`pnpm run demo` starts Claude Code with the mod against made-up PRs: a fake `gh` (`scripts/demo/gh`) answers every GitHub call, and a fake `ghq` knows no clone and a fake `curl` answers with a made-up chart, so nothing real is read or written, and approvals and merges go nowhere. The mod's real state is set aside and put back when you `/exit`. It is also how the screenshot is taken. `DEMO_LANG=ja pnpm run demo` shows the made-up titles, the AI analysis and Claude's answers in Japanese; bot PR titles, descriptions, comments and the menus stay in English.

Tests live in `tests/*.test.ts`. GitHub, the model, the store and the environment are all stubbed, so tests make no network calls.
